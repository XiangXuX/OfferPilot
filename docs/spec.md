# OfferPilot — 产品规格 v0.4（逐项确认中）

更新：2026-09-24；负责人：Sam Xu。Sam 审阅后将本文件放入 GitHub，仓库版本为准。

## 目标用户与要解决的问题

主要服务应届毕业生，也服务部分想换工作的求职者。已有简历常把无关履历、空泛措辞和技能堆在一起，让招聘人员难以迅速看到是否符合岗位关键条件。OfferPilot 对**现有简历与一份目标 JD**做可核对的诊断，由用户决定修改。

**阅读场景（Sam 提出）：** 结果页先服务 HR／招聘人员的初步筛选：快速看清 JD 明列的资格替代关系、年限、核心技术、相关经历、现场办公要求，以及是否明确写了公民／PR 限制。随后提供可展开的项目与技术证据，帮助技术用人经理进一步判断。两种阅读重点可能不同；系统不声称能预测任何公司或个人一定如何筛选，也不自动判定录用资格。

## 本轮用户流程

1. 提交一份**文字可提取的 PDF 简历**，粘贴目标 JD；系统校验、保存并展示输入。原 PDF 供对照，分析标注呈现在网页中的提取文本上。同一份简历可以用于多个 JD；每个简历与 JD 的组合形成独立分析记录。
2. 发起分析；系统展示排队／运行／完成／失败及可重试状态。
3. 先看简洁的 HR 初筛摘要，再逐项查看 JD 要求和对应简历证据、尚未体现或证据不足的技能、无关／可删减或不专业的片段、需要展开的技术细节；建议修改的原文**红色加粗**，旁边说明原因及引用。真正相关且有证据的技术能力应清楚靠前呈现。
4. 查看 JD 明确写出的澳洲／新西兰公民或 PR 限制及原句；若 JD 没写，显示“JD 未说明”。用户接受或忽略建议，自行修改简历；投递后可手动记录状态。

## 业务规则与验收

| 规则 | 可验证的结果 |
| --- | --- |
| 建议和匹配要有依据 | 能定位到简历和／或 JD 的原文；无法核对的 AI 结论不作为确定事实展示。 |
| JD 要求保留层级和逻辑 | 保留 `OR`／替代资格条件，不把各分支误列为同时必须满足。不能只按章节标题判定门槛：职责中明确要求使用的核心技术也可成为技术资格门槛；其他职责用于判断经历相关性。每项标明 JD 来源。 |
| 不同岗位的分析独立 | 同一份简历针对不同 JD 的分析结果和建议审核选择分别保存；一条分析中的接受／忽略不会改变另一条。 |
| 缺少关键词不等于不会 | 分开显示“简历未体现”“证据不足”和用户明确确认“不具备”的情况；系统不替用户确认。 |
| 技能关键词不等于经历证据 | 技能只出现在 Skills 栏时显示“已提及，缺少经历证据”；只有相关经历说明如何使用该技术，才标为“有经历证据”并链接原文。完全未提及时显示“简历未体现”，请用户核实。 |
| 无关内容给出可选择的处理方向 | 对与目标 JD 没有清楚关联的具体简历片段标红加粗，说明原因。若该段真实经历中存在可核实的相关能力，可建议聚焦该部分并改写表达；若没有真实关联，建议剔除。用户选择，系统不自动改原简历。 |
| 审核权属于用户 | 接受／忽略只保存审核选择，不自动改写原简历或生成新简历。 |
| 不编造 | 不虚构技能、经历、项目、技术细节、成果数字或身份资格。 |
| 状态必须可靠 | 后端先校验并保存输入／任务状态，再调用外部 AI 或后台工作；失败可见、重试受控、重复请求不产生重复有效结果，并保留基本审计记录；前端能刷新看到真实状态。 |
| 投递状态手动改变 | 保存简历、创建 JD 或完成分析都不代表已经投递。 |

**端到端验收场景：** 用示例 PDF 和 JD 创建记录、刷新读取、发起分析、查看每条原文证据及红色加粗建议、忽略一条建议、明确标记已投递；再次刷新结果和状态仍在。另用无文字 PDF、AI 失败、重复点击验证错误、重试及去重。

**多 JD 验收场景：** 用同一份简历分别分析 JD A 和 JD B；两个分析各自展示对应 JD 的要求与建议。忽略 A 的一条建议并刷新，B 的建议审核状态保持原样。

**JD 结构验收例子（Sam 提供的 Core Flow AI 文本）：**

| 来源 | 系统应提取和显示 | 解释边界 |
| --- | --- | --- |
| `Qualification requirements` | 本科学历或更高；原文另给“五年相关经验和／或相关厂商认证可替代正式学历”的路径。 | 保留原句和 `OR`／替代关系；不擅自断定单独一张证书必然足够。 |
| `Experience & Other Requirements` | 至少一年相关经验；数据库管理与查询优化；跨职能领导；工程指导（安全编码、API 集成、性能实践）。 | 这是 JD 明列的要求，逐项寻找简历证据；缺少文字不等于候选人不具备。 |
| `Key responsibilities` | 单独、靠前列出 **TypeScript 技术资格门槛**，引用 “Develop and maintain high-quality, scalable software and services using TypeScript.”；再按工作主题整理 AI 模型产品集成、后端／API／数据管道、性能安全与 CI/CD、协作和生产支持。 | 章节标题不决定是否为门槛；明确用于主要开发工作的 TypeScript 必须找证据。其他职责用于判断经历相似性，每个主题可展开到原始 bullet；不把 chat／image／video 推断为三个独立硬性门槛。 |
| `About us`、`Salary and location` 等 | 公司背景不计为候选人资格；记录明确的 North Sydney 现场办公信息。 | “20 million users”是公司自述规模，不是候选人必须服务过该规模的要求。`Only eligible and short-listed applicants` 没写明公民／PR；身份限制显示“JD 未说明”。 |

上述分类是这份 JD 的验收样例，不代替用户核对具体措辞。页面优先显示**正式资格条件和从职责中识别的技术资格门槛**，再显示与其他职责相关的经历证据和缺口，而不是堆满整份 JD 的所有句子。若简历未提供 TypeScript 证据，显示“技术门槛缺少简历证据／需核实”，不能直接断言用户不会 TypeScript 或自动判定其不合格。

**HR 初筛摘要验收例子：** 对这份 JD，首屏突出学历／替代条件、至少一年相关经验、TypeScript、数据库管理／查询优化、跨职能领导、工程指导及 North Sydney 现场办公；公民／PR 显示“JD 未说明”。点击每项可以看到 JD 原句、简历中已有的证据或缺口。AI 产品集成、后端 API／数据管道等经历相似性放在其后的证据层，不让公司背景和长段职责淹没初筛条件。

**TypeScript 证据验收例子（Sam 确认）：** 对上述技术门槛，若 TypeScript 只在简历 Skills 栏出现，结果为“已提及，缺少经历证据”，不能显示为充分匹配；若相关项目或工作经历写明用 TypeScript 完成了什么，并能定位原文，显示“有经历证据”；完全没有提及则显示“简历未体现／需核实”。

**无关片段验收例子（Sam 确认）：** 一段经历与 JD 没有明显联系时，标注具体原文并说明为何不相关。若用户提供的经历里确有与岗位相关的工作，可建议保留真实部分、改写重点；若找不到事实依据，只建议剔除。建议不能把原本未做过的技术工作写成候选人的经历。

## 明确不在本轮

扫描件 OCR、直接改／批注 PDF 页面、生成／导出新简历、自动投递、岗位搜索或 Codex 岗位导入、通用 ATS 百分比、多用户系统、澳洲简历习惯检查和申请提纲。用户自己编辑简历。后续扩展须重新写需求和验收。

## 工程与协作

React + TypeScript + Vite；ASP.NET Core / .NET 10；PostgreSQL + EF Core；Docker；GitHub Actions；Azure 演示。使用轻量 Agile 的优先级 backlog 和逐条反馈；每条 slice 先写 Issue 的行为与验收，再由 Sam 在 VS Code 亲自编码、测试、提交。CI 从基线开始，CD 目标及触发先定，详见 `docs/roadmap.md`。架构取舍放 `docs/decisions/`，AI 协助、Sam 决策和验证放 `AI_USAGE.md`。

## 已确认的细化规则

Sam 已确认下表的 1–4、6–8；第 5 项按 Sam 的纠正明确了 JD 的输入方式，简历 PDF 提取失败后的处理仍待定。上文已确认的多 JD 独立分析、TypeScript 门槛、技能证据和无关内容建议继续适用。

| # | 情况 | 已确认的处理 |
| --- | --- | --- |
| 1 | 红色加粗标注范围 | 优先标具体词组或句子；整段都需要处理时才标整段。每条标注有类别、原因和对应 JD 依据。 |
| 2 | 表述不专业／技术证据不足 | 先看 HR 能否迅速识别岗位相关能力；标出空泛动词、夸饰词、只有技术名词而没有“做了什么／怎么做”的表达；建议补充真实实现细节。数字成果仅在用户有依据时呈现，不强求指标。 |
| 3 | JD 门槛语气含糊 | 保留原句与 `OR`／替代关系；明确核心技术可标“技术门槛”，有歧义则标“需人工核实”，不擅自判断用户不合格。 |
| 4 | 长 JD | 单份 JD 全量提取并引用原文；超出所选模型输入范围时按原章节全部分段处理、合并去重并核对原文。本轮不用向量检索。 |
| 5 | 输入格式 | **JD 由用户粘贴文本，不上传 JD PDF**；简历仍上传 PDF。简历提取失败后的处理方式尚未由 Sam 确认。 |
| 6 | 简历／JD 修改后 | 新输入产生新分析版本，旧结果和审核决定保留用于追溯；不静默覆盖。 |
| 7 | 接受／忽略建议 | 只记录用户对建议的审核选择；“接受”不等于原 PDF 已修改，系统不改简历。 |
| 8 | 最小投递状态 | 手动记录“未投递／已投递／面试中／已结束”，已结束可补充结果；不自动从分析状态推导。 |
