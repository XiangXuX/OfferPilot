# OfferPilot — 范围与开发流程 v0.2（待 Sam 审阅）

更新：2026-09-24。按学习和完成质量推进，不按日历天数承诺功能；原先的 14 天、每天 4–5 小时排期作废。

## 1. 一句话目标与 MVP 边界

用户交一份已有简历 PDF 和目标 JD，得到**有原文依据的诊断**：哪些简历片段可能无关、可删减、表达不专业或缺少技术证据；JD 要求的能力有哪些在简历中有证据、哪些尚未体现；JD 是否明确写了公民／PR 限制。用户逐项审核，自己修改简历，并可手动记录投递状态。系统不生成新简历。

| 本轮必须完成（P0） | 暂不做（P1/以后） |
| --- | --- |
| 单用户演示流程：文字可提取的 PDF、粘贴 JD、保存并重新打开；原 PDF 对照，网页展示提取文本。 | 扫描件 OCR、复杂 PDF 格式修复、多用户账户。 |
| 以简历和 JD 的**具体原文**为依据产生建议、技能证据／缺口与公民／PR 原句；网页对建议修改的简历文字标红加粗；用户接受或忽略建议。 | 改写／导出完整简历、自动投递、岗位爬取或导入、泛化 ATS 分数、澳洲简历习惯检查。 |
| 分析任务持久化状态、失败可见、受控重试、去重、基本审计；用户明确操作后才记录手动投递状态。 | 申请提纲、自动状态同步、复杂协作和运营功能。 |
| 可在本地用 Docker 运行；自动构建／测试；Azure 上用虚构或脱敏数据演示。 | 正式面向公众处理真实简历的服务与长期运营。 |

“简历没写”只表示缺少**可见证据**，不能断言用户不会；不编造技能、项目、业绩或身份资格。PDF 无可提取文字时给出清晰错误。本轮是否允许用户手动修正提取文本，作为输入 slice 的开放决定。

## 2. 采用的流程：轻量 Agile + SDD

这是一个人开发、边学边做的项目，不硬套 Scrum 仪式。**Agile** 管理优先级和反馈：维护有顺序的 backlog，完成一条可演示的 vertical slice 就回顾、调整下一条。**SDD** 管每条 slice 如何动手：先写行为规则和验收例子，再写实现与测试；它不是另一套与 Agile 竞争的日程方法。

每条 slice：GitHub Issue（用户场景、规则、成功／失败验收）→ Sam 解释预期数据流 → Sam 在 VS Code 编码 → 相关自动测试和手动演示 → review、记录取舍与 AI 使用 → 独立 commit／PR → CI 通过。问题可以随时拿来讨论；AI 代写的部分须单独记录并由 Sam 验证。

**完成定义（DoD）：** 该 Issue 的成功和失败例子都通过；数据在刷新后保持；相关测试和 CI 通过；能演示本条从输入到前端结果的路径；`docs/spec.md`／决策记录／`AI_USAGE.md` 在有变化时更新；Sam 能解释关键代码。未满足时继续这条 slice，不靠日期强制切换。

## 3. 有顺序的 backlog：先跑通，再增加判断能力

| 顺序 | 交付的 vertical slice | 最小验收例子 |
| --- | --- | --- |
| 0 基线 | 仓库文档、架构草图和 ADR；前后端骨架、数据库连接、本地 Docker 与 CI 起步。 | 新电脑照 README 能启动；空项目构建通过，PR 有自动检查。只建立下一条所需的骨架。 |
| 1 JD | 粘贴、校验、保存、读取 JD。 | 无效输入被拒绝；有效 JD 保存后刷新仍可读取。 |
| 2 简历 | 上传可提取文字的 PDF，校验、保存、提取、网页预览并保留原件对照。 | 无效／无文字 PDF 给清楚反馈；有效 PDF 刷新后仍可查看提取文本。 |
| 3 分析任务 | 用户发起分析；后端保存状态，再由后台调用 AI；记录尝试、失败、重试和审计；前端显示状态。先用固定响应测试。 | 成功、失败、重复点击及重试都可演示；同一请求不会产生重复的有效分析结果。 |
| 4 有依据的诊断 | 接真实 AI；校验其引用；先展示 HR 初筛摘要（资格、年限、核心技术、地点、明确的身份限制），再展开职责相似性、简历证据／缺口与逐段建议。 | 保留 JD 的 `OR`／替代条件；如该示例中的 TypeScript，技术门槛即使写在职责中也要靠前列出；无关片段可建议剔除，或在有真实依据时建议改写相关重点；每项建议可核对原文，没写不等于不会；建议片段红色加粗。 |
| 5 审核与投递 | 用户接受／忽略建议；手动标记申请状态及时间。 | 审核结果刷新后仍在；保存简历或分析完成不会自动变成“已投递”。 |
| 6 交付 | 集成演示、部署和操作文档，修补前面验收留下的问题。 | 本地与 Azure 演示环境跑通同一核心场景，CI 为绿，演示仅用虚构或脱敏资料。 |

这些是**功能顺序，不是每天的任务**。每做完一条，在 `docs/progress.md` 记已完成的证据、遇到的问题、下一条优先级；必要时重新切小 Issue。第一轮先完成基线、JD 和简历输入；第二轮聚焦分析、审核及演示。轮次没有固定天数。

## 4. 技术与 CI/CD 决策

| 位置 | 当前选型／规则 |
| --- | --- |
| 编码与规划 | VS Code、Git、GitHub Issues；`main` 为稳定分支，一条 slice 对应 Issue 和可读的 commit／PR。 |
| 前端 | React + TypeScript + Vite。 |
| API 与后台任务 | ASP.NET Core / .NET 10；异步执行与状态转换的具体实现写 ADR，先确保数据库状态先于外部调用落地。 |
| 数据 | PostgreSQL + EF Core；迁移进版本库，保存输入、任务状态、结果、审核和必要审计。 |
| 本地环境 | Docker Compose 启动依赖和应用；敏感配置不进仓库。 |
| **CI，基线阶段就建** | GitHub Actions 对 PR 到 `main`、push 到 `main` 运行前端类型检查／构建和后端构建／测试；各 slice 增加相关测试，数据库相关测试在其出现时加入。检查失败不合入。 |
| **CD，规则现在定** | 目标是 Azure 演示环境。`main` 的 CI 成功后产生可部署版本；在 Azure 资源、费用、密钥和访问范围确定后接部署步骤，先由手动批准／触发部署，流程稳定后可改为自动部署演示环境。正式公开服务不在本轮。 |

CI/CD 是从项目开始设计的交付约束：CI 随第一份可运行代码落地；CD 的目标、触发及密钥边界现在写清，实际 Azure 资源选型与部署工作安排在已有可运行应用时。不得把“部署到 Azure”理解为只在最后一天临时处理。

## 5. 编码前尚需做的小决定

- 确定一份虚构或脱敏 PDF + JD 作为贯穿演示的样例；明确 PDF 大小、原件存放和提取文本修正方式。
- 选 AI 提供方、费用上限、超时和密钥管理；AI 输出需由后端核对原文引用。
- 在付费或对外部署前写 Azure 服务／费用／访问控制 ADR。核心流程可先在本地完整完成。

这些选择在相关 slice 开始前定，不阻塞第 0 条基线。大范围变更先改 `docs/spec.md` 的边界和 backlog，再改代码。
